==================================================
PRIMARY GOAL
==================================================

Make the member-owned individual surface/store actually complete end to end.

The intended path is:

member
→ owns channel / surface identity
→ creates products / packets
→ attaches them to that channel
→ shares a real public-facing individual surface
→ public visitors can browse that surface correctly

Right now this is only PARTLY complete.

The member side can create and own channels.
Products and packets can attach to channels.
Public store/channel APIs exist.

But the full connection to a real public-facing member surface is not finished.

This pass must complete that bridge.

==================================================
WHAT IS ALREADY TRUE (DO NOT BREAK)
==================================================

1. Members can create channels.
2. Channels are member-owned (`ownerId`, `type: 'member'`, etc.).
3. Products and packets can attach to `channelId`.
4. Public store/channel APIs already exist, including endpoints for:
   - channels
   - channel products
   - channel collections
   - channel content

Do NOT destroy this.

==================================================
THE CURRENT GAPS
==================================================

Based on this ZIP, these are the major incompletions:

1. MEMBER SHARE URL IS NOT WIRED TO A REAL FRONTEND ROUTE
The member channel UI currently builds share links like:
- `/channel/:channelId`

But the frontend app does NOT currently expose a matching route in `App.tsx`.

That means members are being given a share URL for an individual surface that is not actually routable in the frontend.

This must be fixed.

2. MEMBER IDENTITY FIELDS ARE NOT FULLY ACTIVATED
The onboarding/profile system stores values like:
- `storeName`
- `creatorSlug`

But those values do not yet appear to drive a fully resolved public-facing member surface in a meaningful, canonical way.

3. STORE / CHANNEL / SURFACE RESOLUTION IS NOT FULLY UNIFIED
There are signs that:
- channels may live under a platform store
- products/packets may carry storeId separately
- public store APIs exist independently
But the exact member → store → channel → public surface relationship is not yet explicit enough.

4. MEMBER UX DOES NOT FULLY REALIZE THE COLLECTION LAYER
If the intended model is:
- store
- channel
- collection
- product
then the member-facing flow is still strongest at:
- channel
- mixed items (products + packets)

The collection layer is not yet strongly completed in the member-owned surface flow.

==================================================
TARGET END STATE
==================================================

After this pass, the member-owned surface model must work like this:

A. MEMBER IDENTITY
A member has:
- memberId
- creatorSlug and/or storeName

B. MEMBER CHANNEL

C. MEMBER PRODUCTS / CONTENT

==================================================

Do NOT let:
- packets
- products
- channels
- public store resolution
