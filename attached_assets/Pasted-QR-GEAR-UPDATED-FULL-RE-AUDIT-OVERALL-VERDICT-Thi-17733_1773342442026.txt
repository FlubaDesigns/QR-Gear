QR GEAR — UPDATED FULL RE-AUDIT
===============================

OVERALL VERDICT
---------------
This version is significantly cleaner than the previous one.

Major improvements verified:
- Canon docs now exist
- domain model is explicit
- collectionTag is removed from live code
- program_series is removed from live code
- widget view types now use mosaic_series
- DEFAULT_STORE_ID issue is removed
- Cloud Functions monolith was broken apart
- targeted tests were added

However, the platform is still in a transitional state.

Main remaining issue:
The codebase still has partial legacy persistence and naming carryover:
- site_programs still exists as the storage collection name
- dynamicsCollections still exists as a legacy Firestore collection name
- some partner/widget naming still carries kingdom_connects context
- collection IDs are sometimes still used like display labels instead of canonical IDs
- multi-tenant cleanliness is improved but not fully mature

---------------------------------------------------------------------
2. WHAT IS STILL NOT FULLY COMPLETE
-----------------------------------

A. Legacy persistence model still exists
Verified:
- server/lib/programService.ts
- collection name still = site_programs

Also found in:
- functions/src/routes/widget.ts

Meaning:
Mosaic is conceptually established, but the actual backing persistence still relies on the legacy site_programs storage name.

This is not fatal, but the migration is not fully complete.

B. dynamicsCollections still exists as a legacy Firestore collection name
Verified:
- server/routes/dynamics-content.routes.ts
- functions/src/routes/dynamics.ts
- functions/src/routes/admin-stores.ts

These files use:
- const MOSAIC_TEMPLATES_COLLECTION = 'dynamicsCollections'

Meaning:
The alias pattern is cleaner than before, but the actual Firestore collection name remains legacy.

Again: not fatal, but not fully canon-clean.

C. kingdom_connects naming still leaks into platform internals
Verified:
- server/lib/channelItemsService.ts → PLATFORM_STORE_ID = 'kingdom_connects'
- server/lib/widget-auth.ts → PLATFORM_ISSUER = 'kingdom_connects'
- server/lib/kcWidgetService.ts → KC_PARTNER_ISSUER = 'kingdom_connects'

Meaning:
The code has renamed the identifiers, which is good, but the actual values still point to the older KC context.
This may be intentional for backward compatibility, but it still means platform language and runtime identity are not fully neutral.

D. Some collection IDs appear to be used like labels
Examples found:
- server/routes/misc.routes.ts
  collectionId: "Official"
  collectionId: "Events"

Meaning:
Some “collectionId” values still look like human-readable labels rather than canonical durable IDs/slugs.
That can still create integrity and migration pain later.

E. Old service name still exists
Verified:
- server/lib/programService.ts

Even though mosaicService exists conceptually, the repo still carries the old core service file name.
That keeps the legacy dialect alive in the codebase.

F. Firestore model is cleaner, but still mixed
The repo now clearly uses collectionId broadly, which is good.
But there are still multiple collection/item storage patterns:

Examples:
- collection_items
- dynamicsCollectionItems
- site_programs
- dynamicsCollections

Meaning:
The system is better normalized than before, but not yet reduced to a fully consolidated canonical Firestore naming model.
